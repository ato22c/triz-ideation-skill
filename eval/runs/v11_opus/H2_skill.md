**먼저 에이전트가 고친 뒤에 변경을 파일 단위로 하나씩 되돌려 보고, 되돌려도 테스트가 통과하는 변경은 버리는 "사후 다이어트"부터 해 보세요. 미리 범위를 좁히지 않으니 필요한 수정은 막히지 않고, 상관없는 수정만 걸러집니다.**

### ① 사후 diff 다이어트: 넓게 고치게 두고, 끝난 뒤 깎아내기
- **뭘 하나:** 에이전트가 먼저 "고치기 전에는 실패하는 테스트"를 하나 쓰게 하고, 범위 제한 없이 고치게 둡니다. 작업이 끝나면 스크립트가 바뀐 파일을 하나씩 원래대로 돌린 뒤 테스트를 돌립니다. 그래도 통과하면 그 파일 변경은 필요 없다고 보고 버립니다.
- **왜 내 상황에 맞나:** 미리 막지 않고 나중에 걸러내므로 "범위를 좁히면 실패한다"는 문제가 생기지 않습니다. 흔한 답인 "프롬프트로 건드리지 말라고 하기"와 달리 에이전트가 말을 듣는지에 기대지 않습니다. 테스트 결과가 판정합니다.
- **안 통하는 조건:** 테스트가 약하면 필요한 변경까지 "되돌려도 통과"해서 지워집니다. 그래서 고치기 전에 실패하는 테스트를 먼저 쓰게 하는 것이 꼭 필요합니다.
- **첫 실험:** 개발자 1명이 지난주 에이전트 작업 10건에 git으로 직접 파일을 되돌려 보며 판정합니다(반나절). 걸러진 파일 중 80% 이상이 실제로 상관없는 수정이었다면 스크립트로 만드세요.

### ② 증거를 대야만 범위가 넓어지는 방식
- **뭘 하나:** 처음에는 에이전트가 계획서에 적은 파일만 고칠 수 있습니다. 다른 파일을 고치려면 "이 파일을 가리키는 컴파일 에러, 실패한 테스트, 호출 경로"를 그대로 붙여야 하고, 증거가 붙으면 그 파일이 자동으로 열립니다.
- **왜 내 상황에 맞나:** 흔한 답인 "허용 파일 목록"은 처음 정한 목록이 고정이라 필요한 수정을 막습니다. 이 방식은 목록이 증거에 따라 늘어납니다. 필요한 수정은 보통 에러로 드러나고, 상관없는 수정은 증거를 댈 수 없습니다.
- **안 통하는 조건:** 필요한데 에러로 드러나지 않는 수정(설정·문서·마이그레이션)이 많은 작업입니다. 이런 파일은 사람이 승인하는 길을 따로 둬야 합니다.
- **첫 실험:** 1주일 동안 시스템 프롬프트로만 흉내 냅니다. "계획 밖 파일을 고치기 전에 증거를 출력하고 멈춰라"라고 지시하고 사람이 승인 버튼 역할을 합니다. 범위 밖 수정이 절반 이하로 줄고 작업 실패율이 지금보다 높아지지 않으면 훅이나 권한 설정으로 자동화하세요.

### ③ 버리지 말고 따로 빼기: 변경 묶음마다 이유를 달고 자동 분리
- **뭘 하나:** 에이전트가 변경 묶음(hunk)마다 "요청의 어느 부분 때문인지" 한 줄씩 달게 합니다. 이유가 없거나 요청과 무관한 묶음은 자동으로 별도 "부수 변경" PR로 옮깁니다. 주 PR에는 요청과 관련된 것만 남습니다.
- **왜 내 상황에 맞나:** 흔한 답인 "사람이 diff를 리뷰하며 지우기"는 큰 diff에서 리뷰어를 지치게 합니다. 이 방식은 리뷰 전에 분류와 분리가 끝나 있어서, 주 PR은 짧게 보고 부수 PR은 머지할지 버릴지만 고르면 됩니다. 쓸 만한 리팩터링도 잃지 않습니다.
- **안 통하는 조건:** 에이전트가 그럴듯한 이유를 지어내면 걸러지지 않습니다. 그래서 ①의 테스트 판정과 함께 쓰는 게 안전합니다.
- **첫 실험:** 다음 PR 5건에서 에이전트에게 묶음별 이유를 쓰게 하고 사람이 손으로 나눠 봅니다. 주 PR 리뷰 시간이 절반 가까이 줄면 계속하세요.

### 와일드카드: 같은 일을 세 번 따로 시키고 겹치는 파일만 쓰기 (위험)
- **뭘 하나:** 같은 요청을 서로 독립된 에이전트 3개에게 맡깁니다. 셋 다 고친 파일은 필요하다고 보고, 하나만 고친 파일은 엉뚱한 수정 후보로 표시합니다.
- **왜 내 상황에 맞나:** 사람이 미리 범위를 정하지 않아도 "필요한 범위"가 여러 시도의 공통점으로 드러납니다. 비용이 3배 들고 결과가 들쭉날쭉할 수 있다는 위험이 있습니다.
- **안 통하는 조건:** 세 에이전트가 같은 나쁜 습관(예: 포매터 일괄 적용)을 공유하면 엉뚱한 수정도 "공통"이 됩니다.
- **첫 실험:** 범위 밖 수정이 심했던 작업 3건을 각각 3번 돌려 봅니다(1~2시간). 공통 파일만 남겼을 때 테스트가 통과하는 비율이 2/3 이상이면 계속하세요.

## 근거 (짧게)
- **가정:** 지금 쓰는 에이전트(Claude Code, Cursor 등)는 바꾸지 않고, 모델을 다시 학습시킬 수 없으며, git과 테스트가 있다고 봤습니다.
- **재정의:** "에이전트를 막는다"가 아니라 "최종 머지되는 변경이 요청에 필요한 것만 담게 한다"로 바꿨습니다.
- **제약:** 필요한 수정은 막지 않기, 큰 코드베이스, 리뷰하는 사람의 시간은 한정됨.
- **기술적 모순**(한쪽을 좋게 하면 다른 쪽이 나빠짐): 범위를 좁히면 엉뚱한 수정은 줄지만 작업 성공률이 떨어집니다.
- **물리적 모순**(같은 대상에 반대 성질이 동시에 필요함): 수정 권한은 좁아야 하면서 동시에 넓어야 합니다.
- **연결:** ①은 시간 분리입니다. 작업 중에는 넓게 열고 머지할 때 좁힙니다. ②는 조건 분리입니다. 증거가 있을 때만 넓힙니다. ③은 수준 분리입니다. 레포 전체는 열어 두고 변경 묶음마다 정당화를 요구합니다. 와일드카드는 직접 연결되지 않습니다(공통점을 증거로 쓰는 방식).

## 부록
- **무난한 답(금지 목록):** 프롬프트로 금지하기 / 허용 파일 목록 / 규칙 파일(CLAUDE.md) / 작업 잘게 쪼개기 / 사람이 diff 리뷰 / 읽기 전용 폴더 / 컨텍스트 더 많이 주기 / 더 좋은 모델.
- **IFR**(이상적 최종결과): 엉뚱한 변경이 비용 없이 저절로 사라진다. **자원:** git diff, 테스트, 커버리지, 커밋 이력(함께 바뀌는 파일), 에이전트의 설명 로그, CODEOWNERS(코드 담당자 지정 파일), 의존성 그래프.
- **발산 아이디어:**
  - [분할] 변경 묶음 단위로 이유 달기
  - [추출] 범위 밖 변경을 부수 PR로 떼어내기
  - [범용성] 실패 테스트가 지나는 코드 경로만 수정 허용
  - [중간 매개자] 범위 밖 수정은 승인 에이전트를 거치기
  - [사전 조치] 건드릴 파일 예상 목록 먼저 제출
  - [역동성] 에러가 가리키는 파일만 범위 확장
  - [반대로 하기] 고친 뒤 되돌려 보며 최소화하기(델타 디버깅)
  - [전화위복] 엉뚱한 수정을 결합 지점 지도로 쓰기
  - [피드백] 진행 중 diff 크기를 예상치와 비교해 보여주기
  - [색 변화] 요청 관련도에 따라 diff에 색 표시
  - [불활성 환경] 샌드박스에서 자유롭게 고치고 패치만 추출
  - SKIP: 결합(억지), 열팽창(비유가 안 맞음)
- **극단화**(일부러 극단적인 조건을 걸어 보기): 비용을 무한으로 놓으면 여러 번 실행해 교집합을 씀(와일드카드). 전제를 뒤집으면 범위를 파일이 아니라 "동작 변화"로 판정하고, 에이전트는 수정 의도만 내고 적용은 정해진 규칙대로 도는 도구가 함. 먼 분야 유추로는 수술 부위 표시와 수술 후 기구 개수 확인, 금융의 한도 초과 시 2차 승인을 봤습니다.
