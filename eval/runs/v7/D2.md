# 푸시 알림 딜레마: 새로운 접근 후보

## 1. 추천 3안 + 와일드카드

전제(가정): 사용자끼리 연결(친구·팀·팔로우)이 조금은 있고, 앱 안에 "시간이 지나야 완성되는 것"(결과·새 소식)이 하나쯤 있다고 보았습니다. 안 맞으면 각 안의 "안 통하는 조건"을 보세요.

### 추천 A. 나갈 때 "다음 부름"을 사용자가 직접 예약
- **한 줄 요약:** 앱을 닫기 직전에 "다음에 무엇이 생기면 알려드릴까요?"를 딱 한 건 고르게 하고, 그 건만 알림을 보냅니다. 받는 알림이 전부 "내가 부탁한 것"이 됩니다.
- **왜 뻔하지 않은가:** 흔한 답인 '알림 종류별 수신 설정'은 처음에 한꺼번에 골라 두고 잊습니다. 이 안은 매번 구체적인 한 건을 부탁받는 방식이라, 알림이 광고가 아니라 약속 이행으로 읽힙니다.
- **한계·안 통하는 조건:** 부탁할 만한 "앞으로 생길 일"이 없는 앱(늘 같은 콘텐츠)이면 고를 거리가 없습니다. 고르는 게 귀찮아 참여율이 낮으면 재방문 물량도 줄어듭니다.
- **첫 실험:** 알림 허용 사용자 300명을 무작위로 150/150 나눕니다. 실험군은 종료 화면에 부탁 문구를 넣고, 개발 없이 운영자가 관리 화면에서 수동 예약 발송합니다. 대조군은 지금 방식 그대로입니다. 14일간 봅니다. 성공은 주 1회 이상 방문 비율이 대조군보다 +5%p 이상이면서 알림 끈 비율 차이가 +0.5%p 이하일 때, 실패는 재방문 +2%p 미만입니다. 신청한 사람이 원래 열성적일 수 있으니, 신청 여부와 상관없이 실험군 150명 전체를 비교합니다.

### 추천 B. 앱이 아니라 "사람"이 보내는 알림
- **한 줄 요약:** 앱이 직접 보내는 알림은 최소로 두고, 친구·팀원이 서로에게 "같이 해요"를 보내는 버튼을 알림의 주 재료로 씁니다.
- **왜 뻔하지 않은가:** 흔한 답인 '개인화 타깃팅'은 여전히 앱이 보내는 알림이라 광고처럼 무시됩니다. 이 안은 보내는 쪽이 사람이라, 사용자가 끌 이유가 적은 알림 통로가 하나 더 생깁니다.
- **한계·안 통하는 조건:** 혼자 쓰는 앱이거나 사용자 간 연결이 없으면 성립하지 않습니다. 사람이 보내는 메시지를 남발하면 스팸 취급을 받습니다.
- **첫 실험:** 서로 연결된 100쌍을 무작위로 50쌍/50쌍 나눕니다. 실험군은 한쪽이 상대에게 메시지를 보내면 운영자가 수동으로 중계합니다. 대조군은 같은 내용을 앱 명의로 보냅니다. 14일간 봅니다. 성공은 받은 사람의 48시간 내 방문율이 대조군보다 +10%p 이상이고 알림 끈 사람이 늘지 않는 것, 실패는 +3%p 미만입니다. 인기 많은 사용자 몇 명이 결과를 좌우할 수 있으니 한 사람이 받는 메시지는 최대 3건으로 제한합니다.

### 추천 C. "돌려놓고 나가게" 만들기
- **한 줄 요약:** 앱을 나가기 전에 시간이 걸리는 일 하나를 시작시켜 둡니다. 예를 들어 "내일 아침 ○○ 결과가 나와요"를 실제로 진행하고, 사용자는 알림 없이도 그 결과가 궁금해서 돌아옵니다.
- **왜 뻔하지 않은가:** 흔한 답인 '스트릭·포인트 보상'은 안 오면 잃는다는 압박으로 끌어당깁니다. 이 안은 사용자가 시작한 일이 끝나기를 기다리는 마음으로 돌아옵니다.
- **한계·안 통하는 조건:** 앱에 "진행 중인 일"을 만들 만한 기능이 없으면 억지가 됩니다. 결과가 기대에 못 미치면 다음부터 안 돌아옵니다.
- **첫 실험:** 알림이 꺼져 있거나 미허용인 신규 사용자 400명을 200/200으로 나눕니다. 실험군은 종료 시 "내일 아침 결과가 준비돼요"를 보여 주고 결과는 운영자가 손으로 준비합니다. 대조군은 문구 없음입니다. 두 그룹 모두 이 기능의 푸시는 0건입니다. 7일간 봅니다. 성공은 48시간 내 재방문율이 대조군보다 +8%p 이상, 실패는 +3%p 미만입니다. 요일별 방문 차이가 있으니 두 그룹을 같은 요일에 동시에 시작합니다.

### 와일드카드. "쉬는 동안 쌓아 둘게요" (방치 이자)
- **한 줄 요약:** 알림을 끈 사용자에게는 아무것도 보내지 않는 대신, 마지막 방문 때 "쉬는 동안 놓친 소식을 모아 두었다가 돌아오면 한 번에 정리해 드려요"라고 약속합니다. 오래 쉴수록 돌아왔을 때 받는 정리가 풍성합니다.
- **왜 뻔하지 않은가:** 흔한 답인 '스트릭·보상'은 하루라도 빠지면 손해 보는 구조입니다. 이 안은 늦게 와도 손해가 없고 오히려 더 얻는, 압박의 반대 방향입니다. 다만 보상 계열과 가깝다는 점은 인정합니다.
- **한계·안 통하는 조건:** 쌓아 둘 소식이 별로 없는 앱이면 약속이 빈 말이 됩니다. 이미 떠난 사용자에게는 약속을 본 적이 없어 효과가 없습니다.
- **첫 실험:** 알림이 꺼진 사용자 400명을 200/200으로 나눕니다. 실험군은 다음 방문 때 보여 줄 "쉬는 동안 정리" 화면을 수동으로 만들어 두고, 마지막 방문 때 약속 문구를 보여 줍니다. 대조군은 지금 방식입니다. 30일간 봅니다. 성공은 30일 내 복귀율이 대조군보다 +5%p 이상, 실패는 +1.5%p 미만입니다. 계절·이벤트가 복귀율에 영향을 줄 수 있으니 같은 기간에 동시에 돌립니다.

## 2. 다음 행동

- 비용이 가장 낮은 A(수동 예약 발송)를 먼저 돌립니다. 같은 주에 C도 시작할 수 있습니다(둘은 대상이 겹치지 않게 분리).
- A·C가 모두 실패 기준이면 결과가 빈약한 것이므로 깊게 모드(40개 원리 전수 스윕)로 다시 돌려 보길 제안합니다.

## 3. 근거: 문제 재정의와 모순

- **기능 문장:** "사용자가 알림에 시달리지 않으면서도 자기에게 의미 있는 순간에 스스로 앱으로 돌아온다." "왜?"를 두 번 올려 보면 목표가 "알림 횟수 조절"에서 "돌아올 이유를 알림 밖에서 만든다"로 넓어져, 이 문장으로 갈아탔습니다.
- **모순 쌍:**
  - 기술적 모순(개선하면 다른 게 나빠짐): 알림량이 늘면 재방문은 늘지만 알림을 끄는 사용자도 늘고, 줄이면 그 반대입니다.
  - 물리적 모순(한 요소가 서로 반대 성질을 요구받음): 알림은 재방문을 위해 많아야 하고, 동시에 차단을 피하려면 적어야 합니다.
- **이상적 최종결과(IFR, 비용·장치 없이 목적이 저절로 달성된 상태):** 사용자가 알림 없이도 필요한 순간에 스스로 열고, 알림은 사용자가 부탁한 것만 도착합니다.
- **이미 있는 자원:** 사용자가 앱을 나가는 순간, 사용자 간 관계, 앱이 이미 돌리는 비동기 작업, 안 읽힌 알림 기록과 끈 시점 기록, 쌓이는 미열람 소식, 사용자가 이미 매일 여는 캘린더.
- **추천안과 모순의 연결:**
  - A: 조건 분리(부탁한 조건일 때만 알림) 덕에 "적게 보내면서 재방문은 유지"가 동시에 성립합니다.
  - B: 수준 분리(앱 수준은 적게, 사람 사이 수준은 많게)로 풉니다.
  - C: 시간 분리(앱이 조용한 동안은 진행 중인 일이 대신 부름)로 풉니다.
  - 와일드카드: 시간 분리(조용한 기간과 몰아서 돌려주는 시점)로 풀지만, 보상 계열과 가까워 와일드카드로 두었습니다.
- **가정:** 앱 종류를 알 수 없어 위의 전제(사용자 간 연결 약간, 시간이 걸려 완성되는 기능 하나)를 두었습니다. 알림 허용 사용자 수백 명 규모의 실험이 가능하다고 봅니다.

## 5. 부록

### 5-1. 흔한 답 (제외 기준)
1. 발송 빈도 상한(주 N회)
2. 관심사·행동 기반 개인화 타깃팅
3. 사용자별 최적 발송 시간대
4. 알림 종류별 수신 설정(세분화 옵트아웃)
5. 이메일·문자·카카오톡 등 다른 채널로 대체·병행
6. 스트릭·포인트·배지 등 보상·게이미피케이션
7. 홈 위젯·앱 아이콘 배지
8. 알림 끄려 할 때 "빈도만 줄일까요?" 안내

### 5-2. 추천안별 "가장 비슷한 흔한 답 / 작동 원리가 다른 점"
- A: 4번 수신 설정 / 설정은 사전 일괄 선택이고, 이건 건마다 사용자가 직접 발주하여 모든 알림이 요청에 대한 응답이 됨.
- B: 2번 개인화 타깃팅 / 보내는 주체가 앱이 아니라 사람이라 광고로 분류되지 않음.
- C: 6번 보상 / 손실 공포가 아니라 사용자가 시작한 일의 결과를 기다리는 마음이 재방문을 만듦.
- 와일드카드: 6번 보상 / 안 오면 잃는 구조가 아니라 늦게 올수록 더 받는 구조. 그래도 보상 계열이라 경계선.

### 5-3. 발산 로그 (빠르게 모드: 방향 5개 × 원리 2개)
- #1 [2 추출] 알림 문구를 "다음 사건 한 줄"로 축소 — 문구 모양만 다름(변형)
- #2 [2 추출] 정보 알맹이만 알림, 나머지는 앱 안에서만 공개 — 미끼형 티저
- #3 [31 다공질] 밤·업무 시간 빈 시간대를 사용자가 표시하고 나머지에만 발송 — 발송 시간대 변형
- #4 [31 다공질] 종료 화면·로딩 화면의 빈틈에 다음 방문 이유를 채움 — 열린 고리 → C
- #5 [24 매개체] 사용자가 이미 여는 캘린더에 방문일을 구독 형태로 삽입 — 다른 채널 변형
- #6 [24 매개체] 친구·팀원을 중개자로 삼음 — 사람 발신 → B
- #7 [33 동질성] 알림을 메신저 대화 형식으로 통일 — 모양 변형
- #8 [33 동질성] SKIP(억지: 알림 형식을 통일하는 것 외에 이 문제에 대응되는 발상 없음)
- #9 [9 사전 반대조치] 끄기 전에 미리 사용자가 알림 휴가를 정하게 함 — 일시정지 변형
- #10 [34 폐기와 재생] 안 읽힌 알림은 사라지고 다음 알림에 합침 — 묶음 발송(빈도 변형)
- #11 [22 전화위복] "알림 끔"을 신호로 삼아 끈 사람에게만 다른 경로 제공 — 방치 이자 → 와일드카드
- #12 [22 전화위복] 무시된 알림을 "원치 않음" 라벨로 자동 학습 — 개인화 변형
- #13 [8 무게 보상] 알림 1건마다 사용자에게 돌려주는 가치 1건을 동봉 — 보상 변형
- #14 [8 무게 보상] 알림 부담을 사용자가 주 N장 예산으로 배분해 상쇄 — 알림 예산(보조)
- #15 [32 색·투명도] 알림을 무음·무배지로 두고 앱 안 상태만 색으로 표시 — 배지·위젯 변형
- #16 [36 상전이] SKIP(알림에 "전환점" 개념을 억지로 대응해야 함)
- #17 [극단화: 비용 ∞] 알림 1건이 아주 비싸다고 가정 — 알림 예산
- #18 [극단화: 시간 ∞] 사용자가 영원히 안 와도 기다림 — 방치 이자
- #19 [극단화: 알림 0개] 앱은 부르지 않고 사용자가 앱을 호출 — 다음 부름 예약 → A
- #20 [전제 뒤집기: 누가 보내나] 앱 대신 사람이 보냄 — B
- #21 [전제 뒤집기: 언제 정하나] 앱이 아니라 사용자가 정함 — A
- #22 [먼 분야 유추: 도서관 예약 대기] 원하는 책이 들어오면 알림 — A
- #23 [먼 분야 유추: 방치형 게임] 자리를 비운 시간만큼 복귀 때 몰아줌 — 와일드카드
- #24 [먼 분야 유추: 오븐 타이머] 반죽을 넣어 두고 나가면 시간이 되어 돌아옴 — C
