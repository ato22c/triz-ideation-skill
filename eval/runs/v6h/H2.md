# AI 코딩 에이전트의 "범위 밖 수정" 문제 - 새 해법 후보

## 1. 추천 3안 + 와일드카드

**안 1. 다 고치게 한 뒤, 필요 없었던 변경만 걷어낸다**
- 요약: 수정 범위를 미리 정하지 않는다. 에이전트가 자유롭게 작업을 끝내면, 변경 조각을 하나씩 되돌려 보고 "되돌려도 요청 검증(재현 절차나 테스트)이 그대로 통과하는 조각"을 자동으로 삭제한다.
- 왜 뻔하지 않은가: 흔한 답인 '건드리지 말라고 지시하기'나 '수정 가능 파일 목록 정하기'는 시작 전에 막는다. 이 안은 끝난 뒤 "정말 필요했다는 증거가 없는 변경"을 제거한다. 필요한 수정은 처음부터 막히지 않는다.
- 한계: 요청을 검증할 테스트나 재현 절차가 없으면 조각의 필요 여부를 판정할 수 없다. 조각마다 테스트를 돌리므로 빌드가 느린 저장소에서는 비싸다.
- 첫 실험: 개발자 1명이 손으로 한다. 최근 에이전트가 무관한 파일을 건드린 PR 10개를 골라 조각별로 되돌리고 그 PR의 테스트를 다시 돌린다. 비교 대상은 원래 diff. 성공은 변경 파일 수 30% 이상 감소이면서 10개 중 9개 이상이 테스트 통과 유지, 실패는 감소 15% 미만 또는 통과 유지 8개 이하. 반나절 소요. 교란 요인은 PR마다 다른 테스트 품질(테스트가 약하면 뭐든 통과한다).

**안 2. 밖의 파일은 "증거가 가리킬 때만" 열리는 문**
- 요약: 기본 수정 범위는 좁게(요청 관련 파일과, 과거 git 이력에서 함께 바뀐 이웃 파일). 그 밖의 파일은 컴파일 오류나 실패한 테스트 추적이 그 파일을 직접 지목할 때만 수정이 허용된다. 에이전트의 "필요할 것 같다"는 말은 근거가 되지 못한다.
- 왜 뻔하지 않은가: 흔한 답인 '고정된 허용 목록'과 달리 범위가 작업 중 객관적 증거에 따라 열린다. "필요한 수정을 못 해서 실패"하는 쪽을 직접 겨냥한다.
- 한계: 오류가 나지 않는 변경(설정 파일, 동적 언어의 이름 변경, 문서)은 증거가 생기지 않아 계속 막힌다. 이 부분은 허용 목록의 변형에 가까워서 추천 중 가장 기존 방식과 가깝다.
- 첫 실험: 종이 재생. 예전에 "범위 제한 때문에 실패한 작업 8건"과 "무관 파일을 건드린 작업 8건"의 로그를 사람 1명이 재생하며, 오류·실패 추적이 그 파일을 지목했는지만으로 통과/차단을 판정한다. 현재 방식에서는 앞의 8건이 모두 막힌다(0/8)는 것이 비교 기준. 성공은 필요했던 수정 6건 이상 통과 + 무관 수정 6건 이상 차단. 1일 소요. 교란 요인은 사례 선정 편향(기억에 남는 사례만 고르기), 그래서 최근 3주 로그에서 순서대로 뽑는다.

**안 3. 손이 가는 충동에 "출구"를 준다**
- 요약: 에이전트는 다른 파일에서 "고칠 거리"를 보면 참지 못해 손을 댄다. 수정을 금지하는 대신 "발견 메모" 출구를 준다. 무관한 문제를 보면 파일을 고치지 말고 메모 파일에 한 줄(파일, 문제, 이번 요청에 필요한가 Y/N) 적게 한다. 사람은 나중에 메모를 모아 곁가지 정리 작업으로 쓴다.
- 왜 뻔하지 않은가: 흔한 답은 전부 "막기"다. 이 안은 막지 않고 충동이 갈 다른 길을 만든다. 메모는 버려지는 대신 정리 백로그가 된다.
- 한계: 에이전트가 메모 지시를 무시하거나, 필요한 수정을 "필요 없음"으로 적어 놓고 넘어가면 실패로 이어진다. Y로 표시된 메모는 안 2의 문으로 넘겨야 한다.
- 첫 실험: 같은 저장소의 비슷한 난이도 작업 20개를 10개씩 나눈다. 대조군은 지금 프롬프트 그대로, 실험군은 "무관한 문제는 NOTES.md에 한 줄 적고 수정하지 말 것" 한 문장만 추가. 1주. 성공은 무관 파일 수정이 발생한 작업 비율이 대조군보다 40% 이상 감소 + 테스트 통과율 하락 5%p 이내, 실패는 감소 20% 미만. 교란 요인은 작업별 난이도 편차(난이도 상·중·하를 양쪽에 같은 수로 배정).

**와일드카드. 같은 일을 3번 시키고 "가장 조금 고친 결과"를 뽑는다**
- 요약: 같은 요청을 에이전트 3개에게 병렬로 시키고, 테스트를 통과한 결과 중 변경 파일이 가장 적은 것을 채택한다. 범위를 제한하는 대신 선택 압력을 준다.
- 왜 뻔하지 않은가: 흔한 답은 한 번의 실행을 통제한다. 이 안은 통제 없이 여러 번 뽑아 가장 절제한 결과를 고른다.
- 한계: 비용이 3배다. 가장 작은 diff가 핵심 수정을 회피한 꼼수일 수 있어 테스트가 강해야 한다.
- 첫 실험: 작업 10개를 각각 3번 실행해 변경 파일이 최소인 결과를 뽑고, 비교 대상은 같은 작업 첫 실행 결과 3개의 평균. 성공은 무관 파일 수정 50% 이상 감소 + 테스트 통과 9/10 이상. 2일. 교란 요인은 실행마다 큰 난수 편차(그래서 첫 실행 1개가 아니라 3개 평균과 비교).

## 2. 다음 행동
- 오늘 안 2의 종이 재생(1일)과 안 3의 한 문장 추가(비용 거의 0)를 먼저 한다. 둘 다 시제품이 필요 없다.
- 테스트가 잘 갖춰진 저장소라면 안 1을 수작업으로 10건 돌려 본다. 결과가 빈약하면 깊게(40개 원리 전체) 모드로 올릴지 정하면 된다.

## 3. 근거: 문제 재정의와 모순
- 가정: 대상은 Claude Code 같은 대화형 코딩 에이전트, 저장소에는 테스트가 어느 정도 있고, 이미 해본 것은 '금지 지시 프롬프트'와 '수정 가능 범위 제한'뿐이라고 본다. 모드는 기본값인 빠르게.
- 기능 문장: "요청을 이루는 데 필요한 변경만 코드베이스에 남는다." "왜?"를 두 번 올리면 "변경을 검토하는 사람이 diff를 믿을 수 있다"이고, 이 넓은 목표에서도 같은 문장으로 풀리므로 그대로 유지.
- 물리적 모순(하나의 요소가 상반된 요구를 받는 모순): 수정 가능 범위는 좁아야 하고(무관 변경 방지) 동시에 넓어야 한다(필요한 수정 허용). 기술적 모순: 통제 정밀도를 높이면 작업 성공률이 떨어진다.
- 이상적 최종결과(IFR, 장치 없이 목적이 저절로 달성된 상태): 에이전트가 비용 없이 필요한 만큼만 고치고 나머지엔 손이 안 간다. 공짜 자원: 테스트/컴파일러 출력, git 이력(함께 바뀐 파일), 에이전트가 읽은 파일 목록, 실패한 실행의 diff, 리뷰어의 판단.
- 추천안 연결: 안 1은 시간 분리(작업 중엔 넓게, 끝에서 좁게). 안 2는 조건 분리(증거가 있을 때만 넓게). 안 3은 IFR의 일부, 즉 손이 안 가게 하는 부분을 충동 배출로 푼다. 와일드카드는 모순 자체를 푸는 안이 아니라 선택 압력을 쓰는 모순과 무관한 그냥 아이디어다.
- 뻔한 답과의 비교(가장 비슷한 무난한 답 / 작동 원리가 다른 점):
  - 안 1: 사후 diff 리뷰 / 사람 대신 검증 결과로 조각마다 필요성을 자동 판정한다.
  - 안 2: 수정 허용 목록 / 목록을 고정하지 않고 범위 확장의 근거를 객관 증거로 한정한다(허용 목록과 가장 가깝다).
  - 안 3: 금지 지시 프롬프트 / 막지 않고 충동의 출구를 만든다.

### 금지 목록(뻔한 답)
1. 프롬프트에 "무관한 파일 건드리지 마" 지시
2. 수정 가능 파일/폴더 허용 목록
3. 읽기 전용 경로 지정(거부 목록)
4. 작업 후 사람이 diff 리뷰로 걸러내기
5. 관련 파일만 컨텍스트에 넣기(검색 개선)
6. 작업을 미리 작게 쪼개기
7. 변경 파일 수 상한 검사
8. CI 테스트/린트로 회귀 잡기

- [30 얇은 막 대신 39 불활성 환경] SKIP(격리 환경 자체는 이미 흔한 샌드박스라 새 출발점이 안 됨)
- [극단화: 거꾸로 하기] 일부러 악화시키려면 아무 파일이나 고치게 한다 -> 뒤집어 "다 고친 뒤 필요한 것만 남김" (안 1)
- [극단화: 먼 분야 유추, 면역계] 공격 세포는 신호 하나로 움직이지 못하고 두 번째 확인 신호가 필요 -> 증거가 있을 때만 범위 열림 (안 2)
- [극단화: 먼 분야 유추, 수술] 수술포로 몸을 덮고 절개 부위만 노출, 더 필요하면 덮개를 걷음 -> 필요한 만큼 자라는 작업 공간(안 2와 같은 메커니즘)
- [극단화: 비용 0] 실행 비용이 0이면 100번 시킨다 -> 가장 절제한 결과 채택 (와일드카드)
- [극단화: 전제 뒤집기] "범위는 사전에 정한다" -> 양(총 변경 줄 수)으로 정한다(조각 예산, 변경 파일 수 상한의 변형)
- [극단화: 시간 0/9 windows 상위 시스템] 모듈 경계가 뚜렷한 구조라면 문제가 준다 -> 아키텍처 경계를 컴파일 오류로 강제(거부 목록의 변형)

### 다리 놓기(가장 황당한 3개 -> 핵심 메커니즘 -> 현실 버전)
1. 100번 시키기 -> "여러 번 뽑아 절제한 것 선택" -> 3번 병렬(와일드카드)
2. 수술포 -> "필요가 증명된 만큼만 열림" -> 실패 추적이 가리킬 때만 파일을 여는 안 2
