# 코딩 에이전트의 범위 이탈 vs 필요한 수정 실패: 새로운 해결 방식

## 가정
- 에이전트는 Claude Code, Codex 같은 도구이고, 파일 편집 권한과 훅을 설정할 수 있다고 가정합니다.
- 코드베이스에 테스트, 타입체크, git이 있다고 가정합니다.
- "범위를 좁게 제한"은 지금 허용 경로 목록(allowlist)을 미리 고정하는 방식이라고 이해했습니다.

## 문제의 구조
- 범위를 넓히면 관련 없는 파일을 건드립니다.
- 범위를 좁히면 필요한 수정도 막혀서 실패합니다.
- 원인은 "어디까지 고칠 수 있나"를 작업 시작 전에 한 번만 정하기 때문입니다. 필요한 범위는 작업하면서 드러나는데, 경계는 고정돼 있습니다.

그래서 경계를 넓히고 좁히는 대신, 경계의 성질을 바꾸는 방향이 필요합니다.

## 해결 방식

### 1. 동적 범위: 좁게 시작하고, 근거를 대면 넓힌다
- 처음에는 요청과 직접 관련된 파일만 쓰기 가능하게 둡니다.
- 범위 밖 파일이 필요하면 막고 끝내지 않습니다. 에이전트가 "이 파일이 필요한 이유"를 한 줄로 제출하게 합니다.
- 근거가 객관적으로 확인되면 자동 승인합니다. 예를 들면 다음과 같습니다.
  - 수정 대상이 import하거나 호출하는 파일
  - 실패한 테스트나 타입 오류가 가리키는 파일
- 근거가 약하면 사람에게 넘깁니다.
- 이렇게 하면 필요한 수정은 통과하고, 관련 없는 수정은 근거를 댈 수 없어 걸러집니다.

### 2. 의존 그래프로 허용 범위를 자동 계산
- 사람이 경로를 나열하지 않고, 코드 그래프(import, 호출, 테스트 매핑)에서 "변경 대상의 1~2단계 이웃"을 허용 범위로 계산합니다.
- 범위가 요청에 맞춰 자동으로 달라집니다. 큰 코드베이스일수록 효과가 큽니다.
- 그래프 밖 파일은 2번 방식처럼 근거 제출을 요구합니다.

### 3. 쓰기 제한 대신 사후 변경 검증
- 편집은 막지 않고, 격리된 워크트리나 브랜치에서 작업하게 합니다.
- 종료 시점에 diff를 검사합니다.
  - 요청과 연결되지 않는 변경 파일은 되돌립니다.
  - 파일별로 "왜 바꿨나"를 요청 항목에 매핑해서 매핑되지 않는 변경은 제거합니다.
- 실패하지 않고 정리만 되므로, 필요한 수정이 막혀서 죽는 일이 없습니다.

### 4. 최소 변경을 목표로 하는 검증기
- 테스트가 통과하는 변경 중 가장 작은 것을 선호합니다.
- 각 변경 파일을 되돌려도 테스트가 통과하면 그 변경은 불필요한 것으로 보고 제거합니다. (파일 단위 제거 실험)
- 사람이 범위를 판단하는 대신 테스트가 필요성을 증명합니다.

### 5. 계획 먼저, 파일 목록 합의
- 수정 전에 에이전트가 "바꿀 파일과 이유" 계획을 냅니다.
- 계획에 없는 파일을 수정하려 하면 계획 갱신을 요구합니다. 막는 게 아니라 기록과 재승인을 거치게 하는 방식입니다.

## 추천 조합
1. 기본: 2번(의존 그래프 기반 초기 범위) + 1번(근거 제출 시 확장)
2. 안전망: 3번(격리 워크트리에서 작업하고 종료 시 diff 정리)
3. 선택: 4번(불필요한 변경 제거 실험)은 테스트가 충실한 저장소에서만 사용합니다.

이 조합은 처음에는 좁게 시작하고, 필요가 확인될 때만 범위가 넓어지며, 끝난 뒤에도 남은 불필요한 변경을 정리합니다.

## 도입 순서
1. 먼저 3번(워크트리와 diff 검사)을 적용합니다. 가장 쉽고 위험이 낮습니다.
2. 이탈이 자주 나는 경로를 로그로 모아서 2번의 그래프 규칙을 만듭니다.
3. 훅으로 범위 밖 쓰기를 차단하되 "근거 제출" 경로를 열어 1번으로 확장합니다.

## 주의
- 자동 승인 기준(import 관계, 실패 테스트 등)이 너무 느슨하면 다시 범위가 퍼집니다. 승인 로그를 주기적으로 보고 기준을 조정하세요.
- 동적 생성 코드나 설정 파일 같은 암묵적 의존은 그래프에 안 잡힙니다. 이런 파일은 "항상 사람 확인" 목록으로 따로 관리하세요.
