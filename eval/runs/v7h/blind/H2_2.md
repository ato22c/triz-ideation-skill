# AI 코딩 에이전트가 요청과 무관한 파일을 건드리는 문제 — 새 접근 (빠르게 모드)

**가정:** 코드베이스에 자동 테스트가 어느 정도 있고, 같은 요청을 여러 번 돌릴 토큰 예산은 있다. 이미 해본 "수정 범위를 좁게 제한"은 흔한 답 목록에 넣었다. 모드를 따로 말하지 않으셔서 기본(빠르게)으로 진행했다.

## 1. 추천 3안 + 와일드카드

**추천 1. 넓게 시켜 놓고, 끝난 뒤 필요한 조각만 남긴다**
- 요약: 에이전트가 어디든 고치게 두고, 결과물을 조각(수정 덩어리)으로 나눈 뒤 조각을 하나씩 되돌려 본다. 요청을 검증하는 테스트가 그래도 통과하면 그 조각은 불필요하니 자동으로 뺀다.
- 왜 뻔하지 않은가: 흔한 답인 "작업 후 사람이 diff를 검토"는 사람의 눈으로 걸러낸다. 이 안은 실행 결과로 걸러내고 범위는 사전에 정하지 않는다. 그래서 필요한 수정이 막혀 실패하는 일이 없다.
- 한계: 요청을 검증하는 테스트가 없거나 느리면 못 쓴다. 테스트가 잡지 못하는 필요한 수정(문서, 설정, 타입 선언)까지 지울 위험이 있어 "테스트 밖 조각은 삭제하지 말고 표시만" 해야 한다.
- 첫 실험: 종이 버전(수작업)으로 한다. 최근 에이전트 PR 20개를 골라 한 사람이 조각별로 되돌려 보며 테스트를 돌린다. 비교 대상은 원래 PR 그대로다. 성공은 "테스트 통과율 100% 유지 + 무관하다고 판정된 파일 수 50% 이상 감소", 실패는 그 미만이다. 결과를 흐릴 요인은 PR 난이도 차이인데, 같은 PR의 원본과 삭감본을 짝지어 비교하므로 상쇄된다. 무관 여부는 2인이 따로 판정한다.

**추천 2. 같은 요청을 5번 돌려서, 매번 나온 수정만 채택한다**
- 요약: 같은 요청을 독립적으로 5번 실행한다. 5번 모두에 등장한 파일 수정만 채택한다. 필요한 수정은 매번 반복되고, 엉뚱한 곳을 건드리는 것은 실행마다 제각각이라는 성질을 이용한다.
- 왜 뻔하지 않은가: 흔한 답은 "건드리지 말 곳을 미리 알려 준다"이다. 이 안은 어디가 무관한지 사람이 몰라도 된다. 무관한 수정이 자기들끼리 일치하지 않는다는 점으로 저절로 골라낸다.
- 한계: 유효한 해법이 여러 개라 실행마다 다르게 고치는 요청에는 필요한 수정도 탈락한다. 포맷터 실행처럼 매번 똑같이 생기는 부수 수정은 못 거른다. 비용이 5배다.
- 첫 실험: 요청 10개를 각각 5번 돌려(수동으로 세션 5개) 파일별 등장 횟수를 센다. 비교 대상은 1회 실행 결과다. 성공은 "5회 공통본이 요청 테스트를 통과하고 무관 파일 수가 1회 결과 대비 50% 이상 감소", 실패는 그 미만이다. 교란 요인은 포맷터 같은 체계적 부수 수정이므로 이런 파일은 따로 세어 결과에서 분리한다.

**추천 3. 파일이 아니라 "고치는 방식"을 제한한다 (함수·이름 단위 편집)**
- 요약: 에이전트의 편집 도구를 "이 함수 본문을 바꿔라", "이 이름을 바꿔라" 같은 단위 명령만 받게 한다. 파일은 어디든 열려 있지만, 파일 통째 재작성으로 생기는 포맷 변경·임포트 정리·주변 함수 수정은 구조적으로 불가능해진다.
- 왜 뻔하지 않은가: 흔한 답인 "허용 파일 목록"은 어디를 고칠 수 있는지를 막는다. 이 안은 어떻게 고치는지를 바꾼다. 다른 모듈의 함수 하나가 꼭 필요하면 그 함수만 정확히 고칠 수 있다.
- 한계: 함수 밖(설정 파일, 전역 상수, 스타일 파일) 수정이 잦은 작업에는 맞지 않는다. 편집 도구를 만드는 비용이 든다.
- 첫 실험: 개발 전에 종이로 시뮬레이션한다. 최근 에이전트 PR 20개에서 변경 줄을 두 사람이 "필요/무관"으로 표시한다. 성공은 "무관 줄의 60% 이상이 함수 본문 밖에 있고, 필요한 줄의 90% 이상이 함수 본문 안에 있음", 실패는 그 미만이면 폐기한다. 비교 대상은 현재 방식의 PR이고, 교란 요인은 라벨러 편향이라 2인 독립 표시로 줄인다.

**와일드카드. 코드에 미끼 파일을 심어 "딴 데 손대는 버릇"을 잰다**
- 요약: 요청과 무관하지만 이름이 그럴듯한 미끼 파일(예: 안 쓰는 `legacy_helpers`)을 몇 개 심는다. 에이전트가 미끼를 건드리는 비율로 프롬프트·모델 설정별 이탈 성향을 점수화하고, 성향이 낮은 설정에만 넓은 권한을 준다.
- 왜 뻔하지 않은가: 흔한 답은 모든 에이전트를 똑같이 묶는다. 이 안은 묶지 않고 재서 신뢰한 만큼 푼다.
- 한계: 미끼가 사람 개발자를 헷갈리게 한다. 에이전트가 미끼임을 알아채면 측정이 무의미하다. 측정만 하고 무관 수정 자체는 줄이지 못한다.
- 첫 실험: 테스트용 저장소 복사본에 미끼 3개를 심고, 같은 요청 20개를 두 가지 프롬프트 설정(현재 방식 vs 대안)으로 돌려 미끼 접촉률을 비교한다. 성공은 "두 설정의 접촉률 차이 10%p 이상이고, 접촉률과 실제 무관 수정 파일 수의 상관이 0.5 이상", 실패는 그 미만이다. 교란 요인은 요청 종류 편중이라 두 설정에 같은 요청 20개를 쓴다.

**보조 아이디어 (추천 자리에 못 앉은 것):** ① 막힌 수정 시도를 기록해 범위가 실패에서 자라게 하기(다음 유사 요청부터 자동 포함). ② 무관 수정을 버리지 않고 "별도 제안 PR"로 갈라내기. ③ 실패하는 테스트를 사람이 확인한 뒤 시작하기.

## 2. 다음 행동

먼저 추천 1과 3의 종이 실험을 같은 PR 20개로 한 번에 한다(1~2시간). 두 결과가 다 좋으면 1을 먼저 도구화한다. 테스트가 부실한 저장소면 2부터 한다. 결과가 빈약하면 "깊게" 모드로 올릴지 알려 달라.

## 3. 근거: 문제 재정의와 모순

- **기능 문장:** 요청을 이루는 데 필요한 변경만 결과물에 남긴다. ("왜?" 2번: 범위를 왜 제한하나 → 무관 변경이 섞이지 않게 → 왜? → 사람이 결과를 믿고 반영하려고. 그래서 "반영되는 변경이 요청과 정확히 일치한다"로 넓혔고, 이 목표는 사전 제한이 아니라 사후 판정으로도 풀린다.)
- **물리적 모순(하나의 요소가 상반된 요구):** 수정 범위는 좁아야(무관 파일 보호) 하고 동시에 넓어야(필요한 수정 허용) 한다. 기술적 표현: 안전성을 높이면 성공률이 떨어진다.
- **IFR(이상적 최종결과, 장치 없이 목적이 저절로 달성됨):** 요청에 필요한 변경만 저절로 결과물에 남고 나머지는 사라진다.
- **자원:** 테스트 결과(통과/실패), 남는 실행 시간·토큰, 에이전트의 여러 번 실행 결과, git 이력의 함께 바뀐 파일, 실패·거부 로그, 컴파일러 오류.
- **추천안과 연결:**
  - 추천 1: 시간 분리. 작업 중엔 넓게, 결과물은 좁게.
  - 추천 2: 시간 분리. 각 실행은 넓게, 채택 단계에서 좁게(IFR의 "나머지는 저절로 사라진다"를 다수결로 구현).
  - 추천 3: 수준 분리. 파일 수준은 열고, 줄 수준은 좁게.
  - 와일드카드: 조건 분리. 성향 점수에 따라 범위를 다르게. 모순을 직접 풀지는 못하고 측정을 통해서만 푸는 안이라 와일드카드로만 둔다.

## 부록

### 금지 목록 (뻔한 답)
1. 허용 파일·폴더 화이트리스트 (사용자가 이미 해본 것)
2. 프롬프트에 "관련 없는 파일 건드리지 마" 지시
3. 검색·인덱스로 관련 파일만 컨텍스트에 제공
4. 작업 후 diff 사람 리뷰·승인
5. 보호 경로 읽기 전용 (CODEOWNERS 등)
6. 린트·테스트 통과 강제
7. 작업을 작게 쪼개서 시키기
8. 별도 브랜치·워크트리에 격리
