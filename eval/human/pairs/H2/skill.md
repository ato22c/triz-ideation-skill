**먼저 "건드릴 파일을 선언하고, 선언 밖 파일은 이유 한 줄을 쓰면 열리는" 통행증 방식부터 해보세요. 범위를 막는 대신 "설명 못 하는 수정"만 막는 거라, 필요한 수정은 통과하고 무관한 수정은 스스로 걸러집니다.**

### ① 선언 후 작업 — 이유를 쓰면 열리는 통행증
- 뭘 하나: 에이전트가 작업 시작 전에 "건드릴 파일 목록 + 각 파일을 왜 건드리는지"를 먼저 쓰게 하고, 목록 밖 파일을 편집하려 할 때는 훅(편집 전 가로채는 스크립트)이 "이 파일이 요청과 어떤 관계인지 한 줄" 추가를 요구합니다. 쓰면 바로 허용, 못 쓰면 보류. 사람 승인은 없습니다.
- 왜 내 상황에 맞나: 범위를 사전에 좁히지 않으니 필요한 수정을 못 해서 실패하는 일이 없고, "관련 없는 파일 수정 금지" 지시와 달리 매 편집마다 근거를 강제하므로 포맷 정리·눈에 띈 리팩터 같은 '습관성 수정'은 이유를 못 써 자연히 멈춥니다. 쌓인 이유 로그는 나중에 범위 규칙을 만드는 데이터가 됩니다.
- 안 통하는 조건: 에이전트가 그럴듯한 이유를 아무 파일에나 붙이는 경우(이때는 ③과 결합).
- 첫 실험: 개발자 1명이 1주간 에이전트 작업 10건에 적용 → 요청 무관 파일 변경이 건당 평균 1개 이하로 떨어지고, 과업 성공률이 지금보다 떨어지지 않으면 계속.

### ② 범위를 "폴더"가 아니라 "거리"로 정하고, 막히면 저절로 넓어지게
- 뭘 하나: 요청에 언급된 파일과 그 파일이 직접 import/호출하는 파일(1단계)만 처음에 편집 가능. 테스트가 실패하거나 편집이 거부되면 에이전트가 "확장 요청 + 이유"를 남기고 2단계(한 칸 더 먼 파일)까지 자동 확장. 3단계 이상만 사람이 승인.
- 왜 내 상황에 맞나: 디렉토리 화이트리스트는 사람이 미리 정해야 해서 큰 코드베이스에서는 늘 빠지는 게 생기는데, 이 방식은 범위를 의존 그래프에서 자동 계산하고 "막힘"이 범위를 넓히므로 사전에 맞출 필요가 없습니다.
- 안 통하는 조건: 의존 그래프를 뽑기 어려운 언어/동적 로딩이 많은 코드.
- 첫 실험: 작업 5건을 1단계 범위로 시작, 확장 요청이 자동 승인된 뒤 성공한 비율을 기록 → 5건 중 4건 이상이 2단계 안에서 끝나면 계속.

### ③ 무관 변경을 막지 말고 "분리수거"해 다른 출구로 보내기
- 뭘 하나: 에이전트는 자유롭게 수정하게 두고, 끝난 뒤 두 번째 패스(또는 같은 에이전트)가 diff를 "요청 관련 묶음"과 "그 외 묶음" 두 커밋으로 반드시 나눕니다. 그 외 묶음은 본 PR에서 빼서 "에이전트가 발견한 개선 후보" 드래프트 PR 큐로 자동 이동.
- 왜 내 상황에 맞나: 리뷰 후 수동 되돌리기와 달리 사람이 골라내지 않고, 버리지도 않습니다. 에이전트가 자꾸 건드리는 파일은 보통 실제로 손볼 가치가 있는 부채라서, 그 '고치고 싶은 욕구'를 메인 PR 밖으로 돌려 자산으로 바꿉니다.
- 안 통하는 조건: 요청 변경이 공용 코드의 리팩터와 분리 불가능하게 얽힌 경우(이때 그 묶음은 '관련'으로 둠).
- 첫 실험: 지난 에이전트 PR 10개를 대상으로 수동 분리 → 분리된 "그 외 묶음" 중 리뷰어가 실제로 별도 머지할 가치가 있다고 본 것이 30% 이상이면 자동화.

### 와일드카드: 관련 모듈만 실물이고 나머지는 껍데기인 "축소 사본"에서 작업
- 뭘 하나: 요청 관련 모듈만 실제 코드로 체크아웃하고, 나머지는 함수 시그니처만 남긴 스텁으로 둔 사본 저장소에서 에이전트가 작업합니다. 안 보이는 건 못 건드립니다. 에이전트가 스텁을 고치려 들면 그게 곧 "이 모듈이 필요하다"는 신호가 되어 실물로 교체.
- 왜 내 상황에 맞나: 수정 금지 규칙은 에이전트가 어기지만, 존재하지 않는 코드는 어길 수 없습니다. 디렉토리 제한과의 차이는 "막는다"가 아니라 "보이지 않게 하고, 건드리려는 시도를 확장 신호로 쓴다"는 점.
- 위험: 스텁 생성·빌드 유지 비용이 크고 컨텍스트 부족으로 품질이 떨어질 수 있음.
- 첫 실험: 모듈 1개를 손으로 sparse checkout해 작업 3건 → 3건 중 2건 이상이 스텁 교체 2회 이내로 성공하면 스텁 자동 생성 검토.

2. 그 로그에서 자주 확장되는 파일 패턴을 보고 ②의 1단계 범위 정의에 반영한다.

## 근거(짧게)
- 문제 재정의: "에이전트의 변경이 요청의 의도 범위 안에 머물면서 필요한 변경은 모두 가능하게 한다" → 한 단계 넓히면 "무관한 변경이 메인 브랜치에 들어가지 않게 한다"(생성 시점이 아니라 머지 시점에 풀어도 됨 → ③).
- 제약(가정): 에이전트 자체는 교체 불가, 훅·프롬프트·CI 수준은 수정 가능, git과 테스트가 있는 큰 레포.
- 기술적 모순(한쪽을 좋게 하면 다른 쪽이 나빠지는 관계): 범위 제한 강도↑ → 무관 수정↓, 과업 성공률↓.
- 물리적 모순(한 요소에 반대 성질이 동시에 요구됨): 수정 범위는 좁아야(무관 변경 방지) 하고 동시에 넓어야(필요 변경 허용) 한다.
- 분리(모순을 조건·시간·공간·수준으로 나눠 푸는 길)와 추천안의 연결: ① 조건 분리 — 이유를 쓰면 넓고 못 쓰면 좁다 / ② 공간+시간 분리 — 의존 거리가 가까우면 넓고, 막히는 순간 넓어진다 / ③ 시간 분리 — 작업 중엔 넓고 머지 시점엔 좁다 / 와일드카드: 공간 분리 — 보이는 곳만 넓다.

- [부분·과잉 작용] 범위를 정확히 맞추려 말고 과하게 고치게 둔 뒤 무관 hunk만 사후 보정 → ③의 전신
- [전화위복] 무관 변경을 "발견된 부채" 큐로 전환 → ③

- [열팽창] 테스트 실패 횟수가 오르면 범위가 한 단계 늘고 통과하면 수축 → ②의 자동 확장
- 극단화 ①(당연한 전제 뒤집기): "범위는 사람이 사전에 정한다" → 에이전트가 선언하고 사후에 검증한다 → ①
- 극단화 ②(거꾸로 하기): 두 번째 에이전트가 diff만 보고 "이 변경의 요청은 무엇이었나"를 역추론, 설명 안 되는 hunk가 곧 무관 변경 — ③의 분류기로 재활용 가능
- 극단화 ③(먼 분야 유추): 수술 드레이프(노출 부위만 열기) → 와일드카드 / 금융 거래 한도(소액 자동·고액 승인) → ②의 단계별 승인
- 수렴 점수(새로움/해볼 만함/효과): ① 3/5/4, ② 4/3/4, ③ 4/4/4, 와일드카드 5/2/3
