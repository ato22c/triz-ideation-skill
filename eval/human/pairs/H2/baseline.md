핵심 모순은 "범위를 넓히면 엉뚱한 파일을 건드리고, 좁히면 필요한 수정도 못 한다"는 건데, 이건 **파일 목록(공간)으로 제한하려 해서** 생기는 문제입니다. 제한의 축을 바꾸면 양쪽을 동시에 잡을 수 있습니다. (가정: Claude Code/Cursor류 에이전트 + git 사용 환경)

## 1. 시간으로 분리 — "읽기 단계"와 "쓰기 단계"를 나눔
- 1단계: 에이전트가 수정 없이 코드를 탐색하고 **"건드릴 파일 목록 + 각 파일을 왜 건드려야 하는지"**를 먼저 제출.
- 2단계: 그 목록이 곧 허용 범위. 범위는 사람이 미리 정하는 게 아니라 **에이전트가 조사해서 제안하고 승인받는** 것이라 좁지도 넓지도 않게 됩니다.
- 작업 중 범위를 벗어나야 하면 막지 말고 **"범위 확장 요청"**을 하게 합니다 (사유 1줄). 하드 블록 → 협상으로 바꾸는 겁니다.

## 2. 조건으로 분리 — 3단계 영역
파일을 허용/금지 둘로 나누지 말고 세 구역으로:
- **자유 구역**: 요청과 직접 연관된 모듈. 자유롭게 수정.
- **회색 구역**: 의존성 그래프상 1~2홉 떨어진 파일. 수정은 가능하지만 **사유 기록 필수**, 리뷰 시 별도 표시.
- **금지 구역**: 공용 라이브러리, 설정, 다른 팀 코드 등. 수정 대신 "여기 바꿔야 할 것 같다"는 보고만.

회색 구역은 요청의 진입점에서 import/call 그래프를 따라 자동 산출할 수 있어서 작업마다 손으로 정할 필요가 없습니다.

## 3. 입력 제한 → 출력 검증으로 전환 (가장 효과 큼)
어느 파일을 만지는지 막는 대신, **결과물에 조건**을 걸어요:
- 격리된 git worktree/브랜치에서 자유롭게 작업시키고, 끝난 뒤 diff를 **훙크 단위로 "요청 관련 / 무관"으로 분류**(저렴한 모델이나 규칙으로). 무관한 훙크는 자동으로 별도 커밋/PR로 분리하거나 되돌림.
- "범위 밖 파일을 건드렸으면 그 파일의 기존 테스트가 전부 통과해야 함", "public 시그니처 변경 금지" 같은 **의미 기반 게이트**를 CI처럼 돌림.
- 이렇게 하면 "예방"이 아니라 "사후 분리"가 되어, 필요한 수정은 통과하고 불필요한 수정만 걸러집니다.

## 4. 근본 원인 제거 — 왜 엉뚱한 파일을 건드리는지
큰 코드베이스에서 실제 원인은 대개 이 중 하나입니다:
- **포매터/린터가 저장소 전체에 돌아감** → 변경된 줄에만 적용되게 설정.
- **지나가다 발견한 기존 문제를 "친절하게" 고침** → 지침에 "기존 이슈는 수정하지 말고 보고만 할 것" 명시.
- **import 자동 정렬, 사용 안 하는 코드 정리** 같은 부수 작업 → "요청과 무관한 리팩터링 금지, 하고 싶으면 제안만".
- **탐색 중 길을 잃어 비슷한 이름의 파일을 잘못 수정** → 작업 시작 시 모듈 맵/CODEOWNERS를 컨텍스트로 제공.

AGENTS.md(CLAUDE.md)에 위 규칙을 넣고, 추가로 **"건드린 파일마다 요청과의 연결 사유를 한 줄로 남기기"**를 요구하면 에이전트 스스로 불필요한 수정을 걸러내는 효과가 큽니다.

## 5. 예산 방식
"파일 N개 또는 변경 L줄까지는 자유, 넘으면 멈추고 현재까지 상황 보고" 같은 **범위 성장 예산**을 두면, 작은 작업은 막힘 없이 끝나고 큰 작업만 중간 체크포인트가 생깁니다.
